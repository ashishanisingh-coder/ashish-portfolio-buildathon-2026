## Deployment plan — approval required

Do not run the current `pages.yml` workflow for V5.1. It is the existing V3 production workflow.

After final visual approval:

1. Create a release branch from the approved V5.1 commit; keep `main`, `site/` and `v5/` unchanged.
2. Run `npm ci --ignore-scripts` with Node `24.20.0`.
3. Run `npm test`, `npm run build:v51:pages` and `npm run verify:v51:pages`.
4. Review the generated `dist-v51-pages/` artifact and confirm the manifest base path.
5. Use an approval-gated Pages workflow that uploads `dist-v51-pages/`, not `dist/`.
6. Keep the existing V3 workflow disabled for that release branch; do not push or dispatch anything until approval is given.
7. After deployment approval, verify the public homepage and all four trailing-slash routes, assets, navigation cycle, mobile menu, reduced-motion path, metadata and browser console.
8. If the public site must remain V3, use a separate repository or Pages project for the V5.1 review release rather than replacing the V3 artifact at the existing URL.

## Risks and limitations

- GitHub Pages has no Node server or dynamic route fallback. The four directory-index routes are generated explicitly; arbitrary unknown slugs will not be rendered dynamically.
- The production URL assumes the repository remains named `ashish-portfolio-buildathon-2026`. If the repository name changes, rebuild with `BASE_PATH=/new-repository-name/`.
- GitHub Pages configuration and deployment permissions still require an owner/admin action. No permission or Pages setting was changed.
- Philips and Uno remain truthful source-strip experiences because no separate approved high-resolution panel exports were supplied.
- The V3 public website is still live and must remain the rollback reference until the final approval decision.
